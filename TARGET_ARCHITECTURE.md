# Архитектура telecom-mart

Здесь зафиксировано, как платформа устроена логически и физически, и как разворачивать окружения dev/stage/prod. Писалось для себя и научрука, так что местами детально.

## Логическая схема

### Основные части

- **Источники:** BSS, OSS, CRM, мониторинг — всё что есть у условного оператора.
- **Загрузка:** Airflow с ретраями и алертами, данные льются по расписанию.
- **Lakehouse:** S3 (MinIO) + Iceberg + Trino. Слои: RAW → Validate → DDS → MART.
- **Serving:** ClickHouse, потому что Trino на интерактивных запросах не вывозит по скорости.
- **Фронт:** Django, два дашборда и REST API.
- **AI:** Qwen для Text-to-SQL, SQL Guard режет DDL/DML и лимитирует строки — чисто read-only.

### Как данные идут по слоям

1. Из источников в RAW — как есть, без изменений.
2. Validate — schema check и простые DQ-проверки (полнота, уникальность, свежесть).
3. DDS — доменные таблицы, SCD2 для заказов, client_type через связку с dds_clients.
4. MART — витрины KPI, агрегаты.
5. ClickHouse — serving-таблицы для дашбордов.
6. Django читает ClickHouse.
7. NL2SQL-запросы проходят через SQL Guard и только потом исполняются.

### Правила, которые старались соблюдать

- Схемы версионируются. Breaking change → переходный период, старые и новые колонки живут параллельно.
- Backfill идемпотентно по watermark (иначе при перезапуске DAG'а дубликаты).
- Если DQ-гейт упал — данные не идут в следующий слой. Висит алерт, разбираемся.

## Физически

### Вычисления и хранение

- MinIO хранит RAW/Validate/DDS/MART в формате Iceberg.
- Trino ходит в Iceberg, один инстанс (для MVP хватает).
- Airflow в Docker — scheduler, webserver, triggerer. Worker'ы отдельно если нагрузка вырастет.
- ClickHouse — один сервер, без репликации (опять же, MVP).
- Django отдельно от ETL — чтобы дашборды не ложились вместе с пайплайном.

### Отказоустойчивость (на будущее)

Сейчас по-честному: всё в одном docker-compose, отказоустойчивости нет. В проде должно быть:
- Метаданные Airflow — PostgreSQL с репликацией или managed.
- ClickHouse — хотя бы реплика, а лучше кластер.
- MinIO — erasure coding или хотя бы второй диск.

Пока что спасают retry в DAG'ах и dead-letter для проблемных батчей.

### Сеть и безопасность

- Внутри docker-compose все контуры рядом, но по-хорошему: ingestion отдельно, processing отдельно, serving отдельно от application.
- Секреты в `.env`, не в образах.
- NL2SQL-контур изолирован — SQL Guard не пускает DDL/DML.


- Этот документ — архитектурный baseline.
- Дальше надо: ADR на ключевые решения, deployment-диаграммы, настоящий CI/CD.
- Тудушка на будущее: нормальный мониторинг (Prometheus + Grafana), алерты в Telegram, автоскейлинг ClickHouse.
