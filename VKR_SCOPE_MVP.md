# ВКР: тема, цели и границы MVP

## Что делаем

Тема диплома: **единая витрина метрик телеком-оператора на Lakehouse-платформе**. По сути — собрали данные из нескольких систем в одно место и сделали чтобы на них можно было смотреть без боли.

Конкретно: берём BSS (биллинг), OSS (сеть), CRM (клиенты), мониторинг — льём в озеро, считаем KPI, отдаём на дашборды. Всё воспроизводимо, docker compose up — и поехали.

## Зачем

Проблема которая была: KPI вручную в Excel, данные размазаны по системам, каждый отчёт — квест. Хотели: один источник правды, воспроизводимый пайплайн, self-service.

## Метрики успеха (гипотезы)

- **H1 (скорость):** time-to-insight должен сократиться. Раньше запрос на «сколько абонентов за месяц» — полдня, теперь минуты.
- **H2 (качество):** расхождение между ручным и автоматическим расчётом — в пределах допустимого порога.
- **H3 (self-service):** менеджер сам может открыть дашборд и покрутить фильтры, без привлечения аналитика.

## Что вошло в MVP

- 7 KPI: АБ0, АБ30, АБ90, ARPU, выручка, приток, отток.
- 2 дашборда: «Абонентская база» и «Финансовые показатели».
- Сквозной пайплайн от источников до ClickHouse.
- NL2SQL в read-only с проверкой через SQL Guard.
- Фильтры: сегмент, услуга, тариф, тип клиента.

## Что не вошло (и почему)

- Полный каталог KPI по всем доменам — MVP и так объёмный, остальное потом.
- Серьёзный ролевой доступ — сделали минимальный, для демо хватает.
- Настоящий CI/CD — пока ручной деплой.
- Мониторинг пайплайна — только алерты Airflow, без Grafana.

## Как считаем KPI

### Данные которые есть

Слой DDS в Iceberg (схема `dds`, каталог по умолчанию). Основные таблицы:

| Таблица | Что внутри |
|---------|------------|
| `dds_orders` | Заказы (услуги): статус, даты активации/истечения, владелец, тариф, сегмент |
| `dds_ledgers` | Проводки биллинга: начисления по периодам |
| `dds_clients` | Клиенты: тип (физлицо/юрлицо/ИП) |
| `dds_segments_snapshot` | Справочник сегментов |
| `dds_tariffs_snapshot` | Справочник тарифов |

### АБ0 — активные абоненты на дату

Просто: заказ `ENABLED`, есть дата активации, срок не истёк на дату среза. Считаем `COUNT DISTINCT owner_id`.

Результат: витрина `kpi_ab0_daily`, зерно `report_date × segment × service × tariff × client_type`.

### АБ30 и АБ90 — за 30 и 90 дней

Тут хитрее. Берём заказы, у которых интервал жизни (activation → expire_time) пересекается с окном [report_date − N+1, report_date]. Статус должен быть `ENABLED` или `EXPIRED` (но не `DISABLED`).

Для оптимизации считаем рекуррентно:
- АБ30(D) = АБ30(D−1) + новые(D) − ушедшие(D−29)
- АБ90(D) = АБ90(D−1) + новые(D) − ушедшие(D−89)

Начальное значение для рекуррента — снимок на первую дату окна. Для дней, где рекуррент ещё не накопился — честный COUNT DISTINCT.

### ARPU

ARPU = сумма выручки за окно / активные абоненты на дату среза.

С окном хитро: если дата — последний день месяца, то окно с 1-го числа. Иначе — скользящее окно длиной в календарный месяц.

Выручка нормализуется по типу периода тарифа:
- Месячный тариф → делим на число дней в месяце
- Годовой → делим на 365/366
- Дневной и разовый → без нормализации

Результат: `kpi_arpu_daily`, зерно `report_date × segment × service × tariff × business_center × month_start`.

### Выручка

Дневная: `kpi_revenue_daily` — сумма нормализованных начислений за день по активным заказам.

Периодические: `kpi_revenue_active_month`, `_quarter`, `_year` — строка только на конец периода.

### Приток и отток

- Приток: заказы с `activated` в выбранном периоде.
- Отток: заказы с `expire_time` в периоде или переходом в EXPIRED/DISABLED.

Витрины: `kpi_inflow_daily`, `kpi_outflow_daily`.

## Структура витрин MART

Всё лежит в каталоге `iceberg`, схема `mart`:

| KPI | Таблица |
|-----|---------|
| АБ0 (ежедневно) | `kpi_ab0_daily` |
| АБ30 | `kpi_ab30_daily` |
| АБ90 | `kpi_ab90_daily` |
| ARPU | `kpi_arpu_daily` |
| Выручка дневная | `kpi_revenue_daily` |
| Выручка за месяц/квартал/год | `kpi_revenue_active_month`, `_quarter`, `_year` |
| Приток | `kpi_inflow_daily` |
| Отток | `kpi_outflow_daily` |

Общие разрезы для всех витрин: `segment_id`, `service_kind` (base_type), `tariff_id`, `client_type`, `client_type_title`.

Для ARPU дополнительно: `business_center_id` и `month_start`.

## Как это запускается

Airflow DAG'и в `deploy/compose/airflow/`:
- Загрузка RAW из источников
- `mart_vitrina_runner.py` или отдельные скрипты в `mart_jobs/`
- `mart_serving_clickhouse.py` — репликация из Iceberg в ClickHouse

SQL эталонных запросов: `airflow/scripts/mart_kpi_vitrinas_daily.sql`.

## Критерии готовности MVP

- Пайплайн от RAW до витрин запускается без ручного вмешательства, не падает на DQ-гейтах.
- KPI сходятся с эталонным расчётом в Excel (допустимое отклонение оговорено с научруком).
- Дашборды показывают данные, фильтры работают, drill-down не отваливается.
- NL2SQL работает только в read-only, DDL/DML блокируются.
- Результаты по H1, H2, H3 зафиксированы и готовы к защите.
